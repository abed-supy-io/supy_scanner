# supy_scanner v1.1 — Image-Optimization Roadmap

**Status:** active, 2026-06-17 (draft 2026-06-13). Sprints 1 + 1.5 in progress per `TODO.md`. v1.0.0 ships first (see `TODO.md` S4-07/S4-08); v1.1 work proceeds on its own branch behind the `useNativeCore` flag.

**Goal.** Make scan reliability on low-end Android phones and worn iPhone cameras visibly better than Scanbot, while preserving the frozen `SupyBarcode*` / `SupyDocument*` Dart API. End users see fewer "scan failed", fewer reshoots, fewer manual entries — and they never know why.

**Non-goals.** Cloud OCR. Embedded preview API surface changes. MRZ/ID/check recognition. New paid SDK dependencies.

**iOS** (`ScanbotSDK.xcframework`, arm64, retailer pod 8.0.4-0766c):
- Single Mach-O, **39 MB**.

### 1.3 CV literature distilled

| Problem | Algorithm we'll adopt | Why |
|---|---|---|
| 1D barcode binarization on low contrast | **Wolf-Jolion** (Sauvola variant clamping local σ) | beats raw Sauvola on 1D; field standard |
| 2D barcode binarization (QR/DM/Aztec) | **Sauvola**, window ≈ module-pitch × 3 | field standard |
| Motion-blur on 1D scan | **Wiener deconvolution** with PSF estimated from horizontal gradient autocorrelation (Yahyanejad-Bischof CVPR 2010, +33 pp decode-rate reported) | classical, no model required |
| Data Matrix locator under occlusion | **libdmtx Hough L-finder** (replace ZXing DM locator) | ZXing DM finder requires whitespace centering; libdmtx doesn't |
| 1D locator under partial quiet-zone loss | **zxing-cpp** modern fork (not the legacy Java port) | substantially improved over upstream |
| Live-preview low-light fusion | **3-frame temporal-median fusion on detected ROI** (homography from ORB) | ~5 ms; cheap; large gain handheld |
| Tiny-barcode / small-text upscale | **FSRCNN int8** (~100 KB), patch-only on ROI | ~20 ms on ROI; no full-frame SR cost |
| Document boundary detect | **HED quantized int8** (≤3 MB) — replaces Canny+Hough | ODS 0.79 vs 0.61; what ML Kit/Apple effectively use |
| Perspective correction | `cv::getPerspectiveTransform` + `warpPerspective` bilinear → ≥300 DPI | nothing fancier needed once quad correct |
| Glare removal | **Yang et al. dichromatic specular removal** (PAMI 2015) | pure CPU; no polarizer; no GAN |
| Shadow removal | **Finlayson-Drew-Lu entropy-minimization** (IJCV 2009) | unsupervised; produces intrinsic image |
| Background flatten for OCR | **morphological top-hat** with SE > largest glyph + **CLAHE** | classic, fast, ML Kit-friendly |
| ML Kit / Vision OCR input | denoise + deskew + upscale; **do NOT pre-binarize** | recognizers expect grayscale, not 1-bit |

### 1.4 Architecture recommendation: **Hybrid**

Production scanning stacks (Scandit, Cognex, ZXing forks) all converge on the same shape:

- **Single C++ core**, AOT-compiled to `.a` + `.framework` for iOS and `.so` for Android. Houses: OpenCV-mobile (Apache 2.0, ~15 MB), zxing-cpp (Apache 2.0, ~1.5 MB), libdmtx (BSD-2, ~300 KB), Halide AOT kernels for the 2–3 hot stages (separable blur, warp, adaptive binarize).
- **Platform-native** glue only at the camera and GPU boundary: AVFoundation + Metal Performance Shaders (`MPSImageGaussianBlur`, `MPSImageHistogramEqualization` come free) on iOS; CameraX `ImageAnalysis` (YUV_420_888) + Vulkan compute on Android.
- **Flutter `dart:ffi` for result structs only** — never for pixel data. Frame data stays native end-to-end; only decoded `String` payloads / `SupyDocumentPage` URIs cross the FFI boundary. Avoids the well-known dart:ffi multi-copy issue (dart-lang/language#1862).
- Public Dart API (`SupyBarcodeScannerView`, `SupyScannerChannel.scanDocument`, etc.) does not change — the optimization layer lives behind `io.supy.scanner/v1`.

**Why not pure C++ FFI all the way to Dart?** Pixel buffers crossing dart:ffi means extra copies and lifetime hazards. Stay native.

**Why not pure platform-native (no C++ core)?** Two codebases for the same algorithm = symbology drift + maintenance burden. Scanbot's modular AAR pattern + their iOS self-contained Mach-O is them solving the same problem with one shared core.

**License posture.** Every adopted lib is Apache 2.0 / BSD / MIT. No GPL/LGPL in the runtime path. No paid SDK. Constraint in `CLAUDE.md` ("don't introduce a paid SDK dependency") holds.

## 2. Phased delivery — 8 sprints, ~9.5 weeks core (+~2 wks decision-gated S8)

Each sprint ships independently behind a feature flag in `SupyScanOptions` so we can A/B against the v1.0 path on real retailer devices.

### Sprint 1 — Native core scaffold (1 week)

- Add `native/` to repo: C++17, CMake (Android) + xcconfig (iOS).
- Vendor opencv-mobile (Apache 2.0 build, ~15 MB) — pinned tag.
- Wire JNI bridge on Android, Swift C-bridging-header on iOS.
- One trivial kernel end-to-end (e.g., `nativeGrayscale(YUV) -> ARGB`) to prove the wiring on both platforms.
- Channel surface unchanged. Feature flag `SupyScanOptions.useNativeCore` (default `false`).

**Exit:** v1.0 path still default; native path runs on demand on both platforms; example app has a debug toggle.

### Sprint 2 — Barcode pipeline lift (1.5 weeks)

- Adopt **zxing-cpp** for both 1D and 2D inside the native core.
- Add **libdmtx** for Data Matrix locator (still hand off decode to zxing-cpp for non-DM).
- Implement **Wolf-Jolion (1D) / Sauvola (2D) adaptive binarization** stage (Halide AOT separable kernel).
- Add **3-frame temporal-median ROI fusion** in live-preview path (single-frame fallback if no ROI yet).
- Hot-toggle through `SupyScanOptions.useNativeCore` — when off, fall back to ML Kit / Vision.

**Exit on retailer test sheet (20 SKUs, low-end Android in 200 lux + 50 lux):** decode-rate uplift ≥ 8 pp vs v1.0 path at p50 latency ≤ +25 ms. Numbers recorded in `docs/QA.md`.

### Sprint 3 — Motion-blur + tiny-barcode SR (1 week)

- Wiener deconvolution stage with PSF estimated from horizontal-gradient autocorrelation; applied only when DoQA-style sharpness gate fails (skip cost on sharp frames).
- FSRCNN int8 (~100 KB) patch SR on ROIs below a min-module-pitch threshold.
- TFLite delegate on Android (GPU/NNAPI); CoreML on iOS.

**Exit:** scan distance at which an EAN-13 still decodes increases ≥ 25 % on Moto G Power class; recorded in `docs/QA.md`.

### Sprint 4 — Document pipeline overhaul (1.5 weeks)

- Replace Canny+Hough with **HED-int8** segmentation (≤ 3 MB model, both platforms).
- Quad refinement + `getPerspectiveTransform` warp to ≥ 300 DPI.
- **Finlayson-Drew-Lu shadow removal** + **Yang specular suppression** + **morphological top-hat flatten** + **CLAHE** as the standard `SupyDocumentPage.processedUri` path.
- DoQA-equivalent capture gate: variance-of-Laplacian + tile edge density + tilt — feature-engineered, no model. Auto-snap when score > threshold.
- OCR input policy: pass denoised + deskewed + upscaled **grayscale** to ML Kit / Vision (NOT binarized — both engines prefer that).

**Exit:** OCR character error rate (CER) on retailer's invoice corpus drops ≥ 20 % vs v1.0 path. Numbers in `docs/QA.md`.

### Sprint 5 — Batch barcode dedup + hardening + v1.1.0 (1 week)

- Native batch dedup state machine: payload-hash × position-stable × confidence-decay over a 1.2 s window. Tunable via `SupyBatchBarcodeScanOptions`.
- Memory profile: 10-page document run, 50-iter batch run, 100 open/close. No leaks.
- Binary-size budget check: total native delta ≤ 22 MB per ABI on Android, ≤ 25 MB iOS. (Sanity: well under Scanbot's 39 MB.)
- Tag `v1.1.0`. CHANGELOG entry.

**Exit:** retailer mobile lead signs off on `docs/QA.md` v1.1 scenarios on one low-end Android + one mid-tier iPhone.

## 4. Risks & mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| Native build complexity (NDK toolchain, xcframework) blows up sprint 1 | Medium | Time-box scaffold to 1 week. If at risk, defer Halide AOT to sprint 5 and ship sprint 2's binarizer as plain C++ first. |
| opencv-mobile ABI mismatch with retailer app's other native deps | Low | Vendor opencv-mobile as static lib (`.a` / `.framework`) — no dynamic symbol clashes. |
| FSRCNN model + HED model push iOS bundle past App Store thinning sweet-spot | Low | Both shipped as on-demand resources via `Bundle.url(forResource:)`; total ≤ 4 MB combined. |
| Decode-rate uplift not measurable because v1.0 already meets retailer needs | Low | Sprint 2 gate is decode-rate **at constant latency** — if v1.0 is already at ceiling on the test sheet, ship anyway since the win shows up on the bad-camera tail. |
| Scanbot publishes a parity feature mid-development | Low | We don't track Scanbot. We track retailer device telemetry. |
| dart:ffi accidentally used for pixel data and burns latency | Low | Lint rule + code review checklist: `dart:ffi` allowed for primitives/structs only. |
| Native-toolchain CI cost (NDK, xcframework, opencv-mobile vendoring) overruns | Low (already paid) | Sprint 1 already absorbed this — CI green per `TODO.md` V1-S1-02/V1-S1-03. Follow-up: vendor-pin + license audit of opencv-mobile / zxing-cpp / libdmtx / Halide before Sprint 2 kickoff. |

## 6. Decisions log

- **2026-06-13** — Architecture chosen: **hybrid** (C++ core via JNI / Swift bridge + platform-native camera/GPU). Not pure dart:ffi (pixel-copy hazard), not dual native (drift). Re-evaluate after sprint 2 if FFI scaffold cost over-runs.
- **2026-06-13** — License posture: only Apache 2.0 / BSD / MIT runtime deps. opencv-mobile + zxing-cpp + libdmtx + Halide all qualify. No GPL/LGPL.
- **2026-06-13** — `dart:ffi` is for result structs only. Pixel data never crosses the FFI boundary in either direction.
- **2026-06-13** — Document scanner OCR input stays **grayscale**, not binarized — ML Kit / Vision recognizers prefer that.
- **2026-06-13** — Channel version stays `io.supy.scanner/v1`. v1.1 is a *behavior* change behind a feature flag, not a wire change. A v2 channel would be reserved for a real breaking surface.

### Sprint 8 — Supy-owned multi-page review (decision-gated, ~2 wks)

Closes the largest gap: Scanbot's review sheet with thumbnails, page counter, and per-page Add / Retake / Crop / Rotate / Delete. Today we lean on `VNDocumentCameraViewController` and `GmsDocumentScanning` for this — they own the review UI, which means we cannot offer rescan-low-quality, manual recrop, or rotate-this-page.

**Decision-gate.** Sprint 8 sacrifices the v1.0 "system scanner does the heavy lifting" property. Per `CLAUDE.md`, this needs an explicit decision logged in `TODO.md`'s decisions section before kickoff. Cost vs. benefit:

- **Cost:** owned CameraX + AVCaptureSession capture path; ~2 weeks; ongoing maintenance of one more UI surface; light loss of system-update "free improvements".
- **Benefit:** unlocks rescan-on-low-quality, manual recrop, rotate, delete, reorder — none possible while system scanners own the UI.

**Pre-decision question** (file in §7): does retailer actually need post-capture page editing, or is "good enough on first shot" the real bar?

**New public surface (sketch, finalize at decision time):**

- `SupyDocumentPage.rotationDegrees: int` (0/90/180/270) and `SupyDocumentPage.quad: List<Offset>` (the rectifying quad — needed for recrop UI).
