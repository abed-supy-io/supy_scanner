# V1-S2-05.2 — Halide AOT swap for `supy_core_binarize_luma`

**Status:** design locked, implementation pending.
**Owner decisions (2026-06-16):**
- Packaging: host generator at build time. `libHalide` vendored under
  `native/third_party/halide-17.0.x/<host-triple>/` for the three host
  triples that build the library (macOS-arm64, macOS-x86_64, linux-x86_64).
- Version: pin **Halide 17.0.1** (latest 17.x patch).
- Scope: port `SAUVOLA_2D` only. `WOLF_JOLION_1D` stays on the existing
  C++ integral-image impl until a 1D-code assist path actually consumes
  it (V1-S2-06+).

The C ABI does not change. `SUPY_CORE_ABI_VERSION` stays at 4. Callers see
identical semantics — the swap is invisible above the ABI line.

## Vendoring procedure (one-time per Halide bump)

1. Fetch the three host tarballs from
   `https://github.com/halide/Halide/releases/tag/v17.0.1`:
   - `Halide-17.0.1-arm-64-osx-<sha>.tar.gz`
   - `Halide-17.0.1-x86-64-osx-<sha>.tar.gz`
   - `Halide-17.0.1-x86-64-linux-<sha>.tar.gz`
2. Verify each tarball against the GitHub-published sha256 in the release
   notes. Record the verified hashes in `third_party/halide-17.0.x/README.md`.
3. Extract under the matching `<host-triple>/` subdirectory. Expected layout
   after extraction (relative to each triple): `bin/`, `lib/`, `include/`,
   `share/`.
4. Confirm `lib/libHalide.{dylib,so}` (or the static variant where shipped)
   exists. **Do not commit `lib/libHalide-*.dbg.*` debug variants.**
5. Stage and commit. Expected diff: three top-level directories under
   `third_party/halide-17.0.x/`, no other tree changes.

The `.gitattributes` already has `*.tar.gz binary` — we extract before
committing so individual `.dylib`/`.so`/`.a` files land directly. Do not
commit the original tarballs.

## CMake wiring

`native/CMakeLists.txt` gains:

```cmake
option(SUPY_USE_HALIDE "Use Halide-AOT kernel for Sauvola binarization" OFF)
if(SUPY_USE_HALIDE)
  include(cmake/FindHalide.cmake)
  include(cmake/HalideAot.cmake)
  add_halide_aot_kernel(
    NAME       sauvola_2d
    GENERATOR  halide/sauvola_2d_generator.cpp
    TARGET     ${SUPY_HALIDE_TARGET}   # set by FindHalide.cmake per ABI
  )
  target_compile_definitions(supy_scanner_core PRIVATE SUPY_HAVE_HALIDE_SAUVOLA=1)
  target_link_libraries(supy_scanner_core PRIVATE supy_halide_sauvola_2d)
endif()
```

`FindHalide.cmake` resolves the host triple from `CMAKE_HOST_SYSTEM_NAME`
+ `CMAKE_HOST_SYSTEM_PROCESSOR`, validates the vendored directory exists,
and exposes `Halide::Halide` as an `IMPORTED` target.

`HalideAot.cmake` defines `add_halide_aot_kernel(NAME GENERATOR TARGET)`
which:
1. Builds the generator as a host executable linked against `Halide::Halide`.
2. Adds a configure-time `add_custom_command` that runs the generator with
   `-g <NAME> -e object,h target=<TARGET> -o <build>/halide/<NAME>_<TARGET>`.
3. Wraps the emitted `.o` + `.h` in a `INTERFACE`/`OBJECT` library named
   `supy_halide_<NAME>`.

`SUPY_HALIDE_TARGET` per ABI (from `halide/targets.cmake`):

| Build ABI       | Halide Target string |
|-----------------|----------------------|
| Android arm64-v8a | `arm-64-android` |
| Android armeabi-v7a | `arm-32-android` |
| Android x86_64    | `x86-64-android` |
| iOS arm64         | `arm-64-ios` |

## Generator sketch (`sauvola_2d_generator.cpp`)

The integral-image impl in `native/barcode/binarize.cpp` (V1-S2-05.1) is
the algorithmic reference. The Halide port expresses the same computation
as a pipeline so the scheduler can tile/vectorize per target.

```cpp
#include "Halide.h"
using namespace Halide;

class Sauvola2DGenerator : public Generator<Sauvola2DGenerator> {
 public:
  Input<Buffer<uint8_t, 2>> src{"src"};
  Input<int32_t>            radius{"radius"};   // clamp(min(w,h)/16, 5, 25)
  Input<float>              k{"k"};             // 0.34
  Input<float>              R{"R"};             // 128
  Output<Buffer<uint8_t, 2>> dst{"dst"};

  void generate() {
    Var x, y, xo, yo, xi, yi;
    Func clamped = BoundaryConditions::repeat_edge(src);

    // Squared input via cast to int32 — matches the int64 integrals in the
    // C++ ref but Halide will pick a wider intermediate as needed.
    Func sq;
    sq(x, y) = cast<int32_t>(clamped(x, y)) * cast<int32_t>(clamped(x, y));

    // Box-sum mean/stddev via separable RDom sums over (2*radius+1)^2 window.
    // The C++ impl uses prefix-sum integrals; the Halide impl can equivalently
    // express it as a 2-pass separable sum which schedules well on NEON.
    RDom r(-radius, 2 * radius + 1, -radius, 2 * radius + 1);
    Expr area = cast<float>((2 * radius + 1) * (2 * radius + 1));

    Func sum_y, sum_y2;
    sum_y (x, y) = cast<float>(0); sum_y (x, y) += cast<float>(clamped(x + r.x, y + r.y));
    sum_y2(x, y) = cast<float>(0); sum_y2(x, y) += cast<float>(sq      (x + r.x, y + r.y));

    Func mean   = sum_y  / area;
    Func mean_sq = sum_y2 / area;
    Func var    = max(mean_sq - mean * mean, 0.0f);   // numerical guard
    Func stdev  = sqrt(var);

    Func threshold = mean * (1.0f + k * (stdev / R - 1.0f));
    dst(x, y) = select(cast<float>(clamped(x, y)) < threshold,
                       cast<uint8_t>(0), cast<uint8_t>(255));
  }

  void schedule() {
    // Conservative starting schedule — refine per target with autoschedule
    // (Halide 17 ships `Adams2019`) or manual tile/vectorize.
    src.set_estimates({{0, 1024}, {0, 1024}});
    radius.set_estimate(8);
    k.set_estimate(0.34f);
    R.set_estimate(128.0f);
    dst.set_estimates({{0, 1024}, {0, 1024}});
  }
};
HALIDE_REGISTER_GENERATOR(Sauvola2DGenerator, sauvola_2d)
```

Algorithmic notes:
- The separable-sum approach is O(radius²) per pixel naively but Halide's
  `compute_at` + RDom reordering produces O(1)-per-pixel after CSE on the
  inner RDom loop. The 1D-then-1D sum approach (compute `sum_x` then
  `sum_y` over `sum_x`) is the canonical Halide pattern — port to that
  before benchmarking.
- The C++ reference computes the window radius as
  `clamp(min(w,h)/16, 5, 25)`. We pass it through `Input<int32_t> radius`
  so the same logic can live in the C++ forwarder.
- Output is the same in-place 0/255 binarized luma as today.

## C++ forwarder change

`native/barcode/binarize.cpp` adds a `SUPY_HAVE_HALIDE_SAUVOLA` branch in
`binarizeLuma(...)`:

```cpp
#if SUPY_HAVE_HALIDE_SAUVOLA
#include "halide/sauvola_2d.h"   // emitted by the AOT step
#endif

bool binarizeLuma(uint8_t* luma, int32_t w, int32_t h, int32_t rs,
                  supy_binarize_mode_t mode) {
  if (mode == SAUVOLA_2D) {
#if SUPY_HAVE_HALIDE_SAUVOLA
    return halide_sauvola_2d_dispatch(luma, w, h, rs);  // thin wrapper that
                                                         // builds halide_buffer_t
                                                         // and calls the AOT func
#else
    return sauvola2dIntegralImage(luma, w, h, rs);       // existing impl
#endif
  }
  if (mode == WOLF_JOLION_1D) {
    return wolfJolion1dIntegralImage(luma, w, h, rs);
  }
  return false;
}
```

The integral-image impl stays compiled in — it's both the
`SUPY_USE_HALIDE=OFF` path and the WJ-1D fallback. We never delete it.

## Verification plan

1. **Unit parity test** — `native/test/binarize_halide_parity_test.cpp`
   generates random 8-bit images at 5 sizes (128², 256×384, 512², 1024×768,
   2048²), runs both impls, and asserts max per-pixel delta ≤ 1. Tolerance 1
   accommodates rounding differences between integral-image int64 and Halide
   float intermediates.
2. **Microbench** — `tools/bench_binarize` records per-call µs at the same
   5 sizes on Pixel 8 + iPhone 15 Pro. Acceptance: Halide path ≥ 1.5× faster
   than the C++ integral-image impl on both devices (the whole point of
   this ticket — otherwise the binary-size cost isn't justified). Record
   numbers in `docs/PERFORMANCE.md` under a `### V1-S2-05.2 Halide swap`
   subheading.
3. **Visual diff on real DM samples** — re-run the V1-S2-05.1 QA shots
   from `docs/QA.md` (decoded `Z(`-prefixed serials at 50 lux + held-tilt)
   and confirm decode count is unchanged or improved.

## Decision log

- **2026-06-16** — Packaging: host generator at build time (vs.
  pre-baked AOT objects or Git LFS). Reason: we'll iterate the
  schedule + algorithm in V1-S2-05.4 and want regeneration to be a
  zero-step from a contributor's perspective. Cost: ~200MB in git +
  every contributor needs the host toolchain.
- **2026-06-16** — Version: pin Halide 17.0.1. Reason: last LTS-shaped
  17.x patch, well-tested with NDK r26+ and iOS clang; reproducibility
  benefit over a moving 18/19.
- **2026-06-16** — Scope: Sauvola only. Reason: WJ-1D is shipped but
  unused on any live path (V1-S2-06.2 still uses Sauvola for DM crops);
  porting an unused kernel adds binary size with no decode-rate upside.
